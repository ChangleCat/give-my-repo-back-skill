# 示例：正确返回资源不存在的 HTTP 响应

[English](atomic-task-card.md)

这是虚构的教学示例，不是在诊断本仓库。假设一个小型任务 API 包含 `src/routes/tasks.ts`、`src/services/tasks.ts` 和 `tests/tasks.test.ts`。前置任务卡已经帮助你掌握路由到服务的调用关系以及测试运行方式。已确定的需求是：请求不存在的任务时返回 HTTP 404，同时保持成功响应的约定不变。

---

**编号：** `GMRB-003`  
**状态：** `active`（进行中）  
**依赖：** `GMRB-001`、`GMRB-002`  
**学习目标：** 理解服务层的“未找到”结果如何转换为 HTTP 响应。

## 为什么要做这张卡

一次边界处理可能把正常的“记录不存在”变成意外的服务器错误。通过走通一条失败路径，你将掌握这个 API 在哪里把业务结果转换为 HTTP 行为。

## 预期结果

让 `GET /tasks/:id` 在任务不存在时返回约定的 404 响应，并用回归测试证明。

## 任务边界

- 只处理现有任务查询链路及其测试。
- 保持任务存在时的状态码和响应体不变。
- 暂不修改数据库结构、引入依赖或重做公共错误处理系统。

## 先读哪里

- `src/routes/tasks.ts`：路由在哪里选择响应状态码？
- `src/services/tasks.ts`：服务层怎样表示“未找到”？
- `tests/tasks.test.ts`：现有测试怎样准备数据、调用接口？

## 建议投入

- 预估时间：完成前置任务卡后约 30–60 分钟。
- 前五分钟：打开路由和距离它最近的一条现有测试，在运行任何命令前先写下你预测的路由到服务层执行路径。

这个估计只用于安排时间，不是截止时间，也不属于完成条件。

## 动手前先预测

预测查询不存在的任务目前会返回什么状态码。追踪服务层返回的值，解释路由接下来会怎样处理。指出你认为应该在哪一层把这个结果转为 HTTP 行为，并说明理由。

## 你要完成的工作

1. 使用现有测试环境复现任务不存在时的行为。
2. 添加一条表达约定响应的回归测试，在修改实现前先观察它失败。
3. 在你选定的层做一个范围明确的修改，遵循项目现有写法。
4. 运行相关测试，确认任务存在的场景仍然正确。

## 约束

遵循现有响应体格式。不要把所有异常都变成 404：意外故障必须能够与记录不存在区分开来。

## 如何验证

每项检查都记录为 `pass`、`fail` 或 `not_run`。`not_run` 不能证明代码正确。

| 检查 | 证明内容 | 结果 | 限制 |
| --- | --- | --- | --- |
| 新测试在旧实现上因预期原因失败，在你的修改上通过。 | 已复现并修复回归问题。 | `not_run` | 运行后填写。 |
| 原有的成功场景测试保持通过，且没有削弱断言。 | 原有成功行为得到保留。 | `not_run` | 运行后填写。 |
| 检查修改是否可能把服务层意外故障误判为未找到。 | 意外故障仍能与资源不存在区分。 | `not_run` | 记录检查的执行路径和结论。 |

测试命令以实际项目文档为准；这个虚构示例不假设具体可执行命令。

## 带回哪些证据

- 仓库 revision 或其他稳定的产物标识。
- 不包含秘密信息的相关工作树变更摘要。
- 适用范围：`GET /tasks/:id` 的任务不存在与任务存在路径。
- diff、修改前后的测试输出，以及简短的路由到服务执行路径说明。
- 为什么把修改放在你选择的边界上。

如果后续变更实质影响这条路径、响应约定或本卡使用的测试，应保留这份证据并将其标为 `needs_recheck`。无关的仓库变化不影响它。

## 理解验收

- “未找到”怎样从服务层一路传到响应？
- 为什么把所有错误映射成 404 会掩盖真实故障？
- 如果服务层改变了表示“未找到”的方式，哪些地方需要跟着变？
